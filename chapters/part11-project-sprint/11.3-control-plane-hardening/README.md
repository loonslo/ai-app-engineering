# P3 迭代 1：控制面加固 · 项目章

[全书目录](../../README.md) · [上一章 P2](../11.2-walking-skeleton-deploy/README.md) · [篇首](../README.md) · [下一章 P4](../11.4-execution-plane-launch/README.md)

- **目标**：把最小上线版加固成接口清晰、可测、有评测门禁、依赖故障不崩溃的控制面，并把关键决定写进 `DECISIONS.md`。
- **v3 路径**：P3 / 项目（清单验收）
- **岗位任务 / 面试题型**：T1、T2、T4、T5 / F3、F4、F5
- **节奏**：10 小时，第 9–12 周。
- **前置**：L2（检索）、L3（评测）、L5.1（服务与可靠性）、[11.2](../11.2-walking-skeleton-deploy/README.md)。

## 为什么

最小上线版是“能跑”。招聘方和用户在意的是“出了问题怎么办、改了会不会变差、为什么这么设计”。这一轮不加新功能，只把已有链路变得**可测、可评、可恢复、可解释**。

## 步骤与要点

1. **原生 RAG 核心**：去掉框架胶水，让接口清晰可测。检索、拼装上下文、调用模型、解析输出各自是一个可以单独测试的函数，依赖通过参数传入。本仓库对应的 capstone 改动由 V3-9 完成；若你用自己的项目，请照这个思路改。
2. **边界上的 Pydantic 契约**：请求、响应、工具参数、模型的结构化输出都用 Pydantic 模型校验，非法输入在边界处就被拒绝（返回 4xx），不要让它流进业务逻辑。
3. **评测接进 CI 门禁**（L3）：把 golden set 的回归评测放进 CI，写明阈值；阈值下降要有人决定，而不是静默通过。离线评测用替身，真实模型评测放到定期任务里。
4. **可靠性**：超时、带抖动的重试、降级（见 [5.2](../../part5-production/5.2-reliability-retry/README.md)）；依赖（模型、检索、数据库）故障时返回可读的降级响应，不返回 500 堆栈。
5. **`DECISIONS.md`**：每个关键决定写一条决策记录（[模板](templates/decision-record.md)）：背景、选项、决定、代价、复审时间。至少 3 条，例如“为什么选这个切分策略”“为什么这样降级”“为什么设这个评测阈值”。

## 常见失败

- 只是把代码重命名、没有真的让依赖可注入；
- 契约只写了模型，没有测试非法输入；
- CI 里的评测阈值永远设得刚好能过；
- 降级路径从没被触发过，上线后第一次触发就出问题（用故障注入测一次）。

## 边界

- 本章没有可执行 gate；检查项能否通过取决于你的项目，不能由课程代为证明。
- “评测门禁”只证明回归没有变差，不证明质量好；golden set 太小、太旧时门禁会失效。
