## 为什么做这个 gate

“服务能扛多少”“出事了能恢复吗”是上线前必须回答的两个问题，而答案常被几个小错误带歪：

- 分位数用 `int(q * n)` 取下标，或者被浮点误差多算一位（`0.7 * 10` 是 `7.000000000000001`）；
- 错误率只数 5xx，漏掉限流（429）和超时；
- 错误预算的允许失败数被浮点误差少算一个（`(1 - 0.9) * 10` 不是整数 1）；
- 容量只算实例数，忘了先撞上的是模型厂商的 RPM / TPM 限额；
- 恢复演练只写“有备份”，没有量恢复时间和丢失的数据，也没跑恢复后的冒烟检查。

## 概念

- **延迟分位数**：p50 是典型请求，p95、p99 更接近用户在最差时刻的感受；平均值会被少数慢请求和大量快请求同时掩盖。本章用**最近秩法**：排序后取第 `ceil(q·n)` 个。
- **错误率**：压测里把 5xx、429（被限流）、超时都算失败。429 要单独计数，因为它指向容量而不是 bug；对应的处理见 [5.2](../5.2-reliability-retry/README.md)。
- **SLO 与错误预算**：SLO 是你承诺的目标（如 p95 ≤ 2 秒、可用性 99.9%）；错误预算是“目标允许的失败次数”，99.9% × 10 万次请求允许 100 次失败。预算用完就应暂停发布、先修稳定性。
- **容量规划**：实例数 = ⌈峰值 rps × (1 + 余量) ÷ 单实例 rps⌉；同时检查按 `峰值 rps × 60` 算出的每分钟请求数和乘以每请求 token 数后的每分钟 token 数，会不会超过模型的 RPM / TPM 限额。真实限额因厂商、套餐和时间而异，一律以当时的官方文档或控制台为准，课程里的数字只是示例。
- **恢复演练**：RTO 是能接受的最长恢复时间，RPO 是能接受的最长数据丢失窗口。演练要实际恢复一次，量出两个数，再跑冒烟检查，才算通过。

## 任务

实现 `gate/starter.py`：

| 接口 | 你要交付的行为 |
|---|---|
| `RequestResult` | 已给出：`latency_ms`、`status`（0 表示超时） |
| `percentile` | 最近秩法；空输入或 q 不在 (0, 1] 时 `ValueError` |
| `summarize_load` | p50 / p95 / p99、错误率（含 429、5xx、超时）、rps、按类型计数 |
| `check_slo` | 返回未达标项（`p95_ms`、`error_rate`），恰好等于算达标 |
| `error_budget` | 允许失败数、已用比例、是否耗尽 |
| `plan_capacity` | 实例数、RPM / TPM 需求、瓶颈（`none` / `rpm` / `tpm`） |
| `restore_drill` | 是否通过、失败项（`backup_exists`、`rto`、`rpo`、`smoke`） |

关键口径见 `starter.py` 各函数的 docstring；几个容易写错的约定：

- 分位数与实例数、允许失败数都要先 `round(..., 9)` 再取整，抵消浮点误差；
- `exhausted` 是“失败数超过允许数”，恰好用满不算耗尽；
- 两项限额都撞上时，取“需求 ÷ 限额”比值更大的那项，比值相等选 `rpm`。

## 概念地图

- **分位数**：最近秩，注意浮点。
- **错误率**：5xx、429、超时都算。
- **SLO / 错误预算**：目标 → 允许失败数 → 用完就停发布。
- **容量**：实例数与模型限额都要算，谁先撞上谁是瓶颈。
- **恢复**：RTO、RPO、冒烟检查，要实际演练。

## 边界

- gate 只验证计算，不验证压测怎么做、数据怎么采集，也不验证真实服务的容量。
- 容量规划是线性估算：没有考虑突发、重试放大（限流时重试会进一步增加负载）、多个租户共享同一份厂商限额、冷启动与缓存命中率变化。
- 本章没有给出任何厂商的真实限额数字；示例数字只用于演示公式。
- 恢复演练的判定只看你填的数字是否可信；备份本身是否可用、数据是否一致要靠真实演练和校验。
