## 为什么做这个 gate

选型最常见的错误是套口诀：

- 知识常变/要引用/模型不掌握，却只改 Prompt；
- 需要固定行为，但样本不足/训练不可行，却硬上微调；
- 把微调当动态知识库；
- 只给方案，不给上线前检查项。

这个 gate 用需求约束组合，验证四种起始方案和检查项。

## 任务

实现 `gate/starter.py` 的 `decide` 和 `recommend`：

| 函数 | 你要交付的行为 |
|---|---|
| `decide` | 检索需求/微调前提 -> Prompt/RAG/微调/组合；返回 reasons + checks |
| `recommend` | 简化入口，返回 `"策略：理由"` |

关键口径：

- `needs_retrieval = 知识常变 or 需要引用 or 模型缺知识`。
- `can_fine_tune = 需要固定行为 and 样本足够 and 训练可行`。
- 两者都真 -> `RAG + 微调`；只检索 -> `RAG`；只微调 -> `微调`；都假 -> `Prompt`。
- `production_checks` 至少 3 条；可微调时追加基座对照/许可/回滚。

## 故障注入（必须亲手触发）

| # | 注入 | 期望 |
|---|---|---|
| 1 | 全部 False | Prompt |
| 2 | 三种检索条件任一 True | RAG |
| 3 | 固定行为+样本+训练可行 | 微调 + 基座检查 |
| 4 | 检索+微调都满足 | RAG + 微调 |
| 5 | 训练不可行 | 不选微调 |
| 6 | 简化入口 | `RAG：...` / `微调：...` |

## 决策顺序与各方法解决什么

**默认顺序：先 Prompt，再 RAG，再工具，最后才是微调。** 每往后一步，成本、数据要求和维护负担都更高，也更难回滚；前一步没试过、没评测过，就不要跳到后一步。

| 方法 | 解决什么 | 需要什么数据 | 主要成本与风险 |
|---|---|---|---|
| Prompt | 指令、格式、风格、少量示例 | 几条到几十条示例 | 最便宜；上下文变长会增加 token；行为不稳时要靠评测发现 |
| RAG | 知识更新快、需要引用、模型不掌握的私有知识 | 文档与检索评测集 | 检索质量决定上限；要维护索引与权限（见 L2、L5.4） |
| 工具 | 需要实时数据或执行动作 | 工具定义与权限设计 | 安全与可靠性成本（见 L4） |
| 微调（全量或 LoRA） | 固定的行为、风格、格式，或把稳定任务迁到更小的模型 | 高质量的输入—输出样本；数量与质量都要评估 | 训练与评测成本；基座升级后要重训；**不是动态知识库**，知识更新仍靠检索 |
| 蒸馏 | 用强模型的输出训练小模型，降低推理成本与延迟 | 强模型生成的样本，需要抽检质量 | 学生模型上限受老师与样本影响；要检查许可条款是否允许用输出训练 |
| 量化 | 压缩模型以便在更小的硬件上推理 | 校准数据（视方法而定） | 可能损失精度，要用你自己的评测集对比；属于部署优化，不改变模型“知道什么” |
| 强化微调 | 用评分函数（奖励）而不是标准答案来优化行为，适合能自动判定对错的任务 | 可靠的评分器与任务集 | 评分器有漏洞会被模型钻空子；技术雷达 Vol.34 在讨论智能体强化学习环境时强调奖励要“可验证、抗作弊”（verifiable and resistant to gaming） |

以上是各方法的一般性描述，用来帮你判断“该不该走到这一步”，不是对某个厂商产品的说明；具体数据量、价格、支持哪些模型，以你使用的平台当前文档为准。

**小模型的位置。** Thoughtworks 技术雷达第 34 期（2026-04）把 **Small language models** 列为 Assess：小模型在某些场景下开始提供比大模型更高的“每美元智能”，团队在评估它们以降低推理成本、加快智能体流程。Assess 意味着值得探索，不代表可以默认替换（来源：[技术雷达](https://www.thoughtworks.com/en-ca/radar/techniques/summary/small-language-models)，读取于 2026-10-31）。落到选型上：先在你自己的评测集上比较，再决定是否把简单、稳定的任务路由给小模型（路由见 [5.3](../../part5-production/5.3-cost-cache-routing/README.md)）。

**6.2 的 LoRA 实操是选修。** 只有当你的目标岗位需要自己训练模型，或你已经按上面的顺序走到“前几步都不够”时，才去做 [6.2](../6.2-lora-finetune-optional/README.md)。其核心概念已经并入本页。

## 边界

- gate 只验证选型规则，不证明方案在真实业务有效。
- 通过 gate 不替代离线评测/线上观测。
- 各方法的数据与成本描述是一般性说明，没有给出具体数字，也没有逐个平台核实支持范围。
- 本章没有改动 gate 与参考实现。
