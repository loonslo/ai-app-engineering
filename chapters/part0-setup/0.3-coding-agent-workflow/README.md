## 问题

进入 2026 年，现代编码 Agent 已经成为工程师日常研发的核心工具。但大模型具有本质上的不可靠性：
- 盲目相信 Agent 的代码补全，极易引入“幻觉 API”、边界防御丢失、敏感数据明文泄漏甚至静默放宽测试断言；
- 缺乏明确规范约束时，Agent 在重构中往往随意改动历史模块、污染环境配置；
- 在技术面试与实际团队协作中，工程师的核心壁垒不再是敲代码的速度，而是对需求边界的定义能力、对项目契约（AGENTS.md）的约束能力，以及严谨的人工 diff 审查与防御性复核能力。

## 概念

### 1. 编码 Agent 的标准工作循环
编码 Agent 执行研发任务时通常遵循闭环流程：
```text
  ┌──────────────┐      ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
  │ 1. 检索与读码 │ ───> │ 2. 制定计划   │ ───> │ 3. 修改代码   │ ───> │ 4. 运行验证   │
  └──────────────┘      └──────────────┘      └──────────────┘      └──────────────┘
         ▲                                                                   │
         └─────────────────────── 失败重试 / 调整计划 ─────────────────────────┘
```
1. **检索与读码**：定位目标代码、调用方与测试用例，建立上下文；
2. **制定计划**：拆解实现步骤、接口改动与测试覆盖策略；
3. **修改代码**：按计划在工作区应用文件变更；
4. **运行验证**：执行测试脚本或 Lint 检查，遇到错误读取信息迭代修复。

### 2. 五大典型失败模式
1. **编造虚假 API（Hallucinated APIs）**：引用不存在的第三方库函数或错误参数；
2. **改坏无关代码（Collateral Damage）**：重构时误改相邻逻辑、修改异常类型或破坏历史注释；
3. **测试只覆盖乐观路径（Self-Fulfilling Tests）**：Agent 补测时倾向于只测正常入参，遗漏边界、越界、空值与异常路径；
4. **引入安全与合规隐患（Security Pitfalls）**：在日志中明文打印密钥或工单数据、引入有漏洞的废弃包；
5. **悄悄放宽测试断言（Weakening Assertions）**：测试失败时不修实现，反而将严格断言改为宽泛断言甚至注释断言以制造“全绿”假象。

### 3. 项目级规范文件（AGENTS.md）的契约作用
大型语言模型进入陌生代码库没有任何技术栈与边界禁令的先验知识。`AGENTS.md` 是给 Agent 的“入职手册”：
- **明确代码边界**：标明冻结快照目录与历史练习，禁止无故重构；
- **配置与安全底线**：严禁把密钥写入代码或测试，只通过环境变量或本机 `.env` 读取；
- **验证契约**：明确离线替身与真实调用的区别，禁止因“文件存在”臆测任务完成。

### 4. 面试中的 AI 辅助编码轮评分标准（以 Meta 官方报道为例）
根据 Meta 公开技术报道（Meta Careers / Engineering Blog，读取日期：2026-10-27），考官关注四大维度：
1. **解题与思路（Problem Solving）**：能够清晰拆解系统与算法逻辑，提供结构化 Prompt；
2. **代码质量（Code Quality）**：审查生成代码的可读性、分层合理性与异常规范；
3. **验证与复核（Verification）**：主动设计反例与对抗用例检查 AI 输出，不看到全绿就交卷；
4. **沟通与协作（Communication）**：口头讨论 Trade-offs，把 AI 当成结对助手而非替罪羊。
> [!IMPORTANT]
> 很多国内企业明确禁止白板面试使用 AI 工具，面试前务必核对考场规则。

## 流程

使用编码 Agent 协作开发必须遵循“防御性研发流程”：
1. **划定边界**：在项目根目录提供 `AGENTS.md`，写明不可修改文件、测试命令与安全约束；
2. **读码并先出计划**：先要求 Agent 输出方案设计与修改范围，人工确认合理后再准许写代码；
3. **最小范围实施**：单次改动严格聚焦于单一功能，避免大规模无节制重构；
4. **自动化独立验证**：脱离 Agent 提示词，工程师亲自运行测试与 Lint 命令；
5. **人工 Git Diff 逐行审查**：按审查清单逐项检查需求完整性、范围克制性与防御断言。

## 练习

在微型代码库 `practice_repo/` 中演练：
- `models.py`：工单数据模型与状态枚举；
- `storage.py`：初始工单假数据；
- `service.py`：工单业务逻辑（未完成状态）；
- `TASK.md`：需求说明书（支持分页、按状态筛选以及严格参数校验）；
- `check_task.py`：断言式检查脚本。未打补丁退出码 1，满足需求退出码 0。

### 操作步骤
1. **创建独立演练副本**：
   在工作区创建 `.tmp/practice/` 并将 `practice_repo/` 整体复制过去，**不修改仓库原件**：
   ```bash
   python -c "import shutil; shutil.copytree('chapters/part0-setup/0.3-coding-agent-workflow/practice_repo', '.tmp/practice', dirs_exist_ok=True)"
   ```
2. **引导 Agent 制定计划**：
   在 `.tmp/practice/` 下要求 Agent 先阅读 `TASK.md` 并列出修改计划，记录到 [workbook.md](workbook.md)；
3. **执行修改与验证**：
   让 Agent 修改 `service.py`，运行检查脚本：
   ```bash
   python .tmp/practice/check_task.py
   ```
   排查错误直到全部通过（退出码 0）；
4. **独立人工审查 diff**：
   审查 Agent 的改动，在 [workbook.md](workbook.md) 中指出至少 3 处需人工复核的点，并定位至少 1 处潜在缺陷。

## 边界

- **非真实生产工单系统**：`practice_repo` 仅为本地内存数据模拟，未涉及数据库连接与真实并发锁；
- **绝对禁止交给 Agent 的场景**：生产环境密钥凭据、真实用户 PII 隐私数据、不可逆的高危生产操作（`DROP TABLE`、无确认批量删除）绝不能发送至公网模型上下文；
- **通过 check_task 不等于无缺陷**：自动化脚本只能覆盖设计好的断言，真实工程质量依赖严密的人工审查。
