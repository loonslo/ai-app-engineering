## 1. 编码 Agent 的工作循环与常见失败模式

进入 2026 年，现代编码 Agent（如 Claude Code、Cursor Agent、GitHub Copilot Workspace 等）已经不仅是单行代码补全工具，而是具备完整开发循环的自动化代理。

### 1.1 标准工作循环

编码 Agent 在执行软件研发任务时，通常遵循闭环流程：

```text
  ┌──────────────┐      ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
  │ 1. 检索与读码 │ ───> │ 2. 制定计划   │ ───> │ 3. 修改代码   │ ───> │ 4. 运行验证   │
  └──────────────┘      └──────────────┘      └──────────────┘      └──────────────┘
         ▲                                                                   │
         └─────────────────────── 失败重试 / 调整计划 ─────────────────────────┘
```

1. **检索与读码（Context Retrieval & Code Reading）**：定位目标代码文件、关联调用方与测试用例，构建任务上下文。
2. **制定计划（Planning）**：拆解实现步骤、接口改动与测试覆盖策略。
3. **修改代码（Code Editing）**：按计划在工作区应用文件变更。
4. **运行验证（Test & Verification）**：执行测试脚本或 Lint 检查。若报错则读取错误信息回溯修正，直到验证通过。

### 1.2 典型的失败模式（为什么不能盲信 Agent）

Agent 在自动化执行时极易产生“看似正确实则危险”的输出。常见失败模式包括：

1. **编造虚假 API（Hallucinated APIs）**：引用了第三方库并不存在的方法或参数（如假想参数 `response.json(parse_float=...)`）。
2. **改坏无关代码（Collateral Damage）**：重构目标函数时无意修改了相邻逻辑、改变了异常类型或丢失了原有的关键边界条件。
3. **测试只覆盖自己写的乐观路径（Self-Fulfilling Tests）**：Agent 为自己新写的代码补测试时，往往只测正常参数，不测越界、None、非法输入或并发竞争。
4. **引入安全与合规隐患（Security Pitfalls）**：在异常日志中把敏感数据或入参直接打成字符串；引入带有已知漏洞的废弃库；写出 SQL 拼接或硬编码密钥。
5. **悄悄放宽测试断言（Weakening Assertions）**：当遇到测试跑不通时，部分 Agent 不去修代码，反而把 `assert result == expected` 改为 `assert result is not None`，甚至注释掉原有的断言以制造“全绿”假象。

## 2. 项目规范文件（`AGENTS.md` / `CLAUDE.md`）的作用与写法

大型语言模型在进入一个陌生的代码库时，没有任何关于该项目技术选型、架构分层、运行环境和安全禁令的先验知识。**项目级说明文件（如 `AGENTS.md`、`CLAUDE.md`）是给 Agent 的“入职手册”与“防御规则”**。

以本仓库根目录的 [AGENTS.md](../../../AGENTS.md) 为例，它确立了清晰的边界契约：
- **代码边界**：哪些目录是冻结快照不可修改（如 `flagship-project/`），哪些属于可独立运行的练习，避免 Agent 自作主张统一重构。
- **配置与安全底线**：严禁把真实模型密钥写进代码或测试，只通过环境变量或本机 `.env` 读取。
- **验证契约**：明确离线替身（Mock）与真实模型运行的区别，要求在任务完成前必须执行指定的命令，禁止因“文件存在”就臆测完成。

好的 Agent 说明文件应具备以下特征：
- **简短且约束具体**：避免冗长废话，写清禁止项、常用运行命令和目录边界。
- **防御性指令**：明确告知 Agent“不要做什么”（例如“禁止重命名旧目录”、“测试只能离线运行”）。

## 3. 人工 diff 审查清单（Code Review Checklist）

在把 Agent 生成的改动提交或合并之前，工程师必须人工进行完整审查。以下是核心审查维度：

1. **需求是否严格对齐**：是否精确实现了需求说明中的每一条边界规则，没有遗漏需求，也没有“过度工程”添加无关功能。
2. **改动范围是否克制**：检查 Git diff 是否只改动了目标模块；是否混入了无意格式化、无关重构或删减了历史注释。
3. **测试是否覆盖防御路径**：是否有针对边界值（0、负数、越界页码、非法字符、None 等）的测试；断言是否足够严密，有没有被偷偷放宽。
4. **依赖与安全性**：是否引入了不必要的第三方依赖；是否有敏感信息、报错信息是否脱敏。
5. **回滚友好性**：若线上运行出现问题，改动能否平滑回滚，是否破坏了既有调用方的兼容性。

## 4. 面试中的 AI 辅助编码轮评分与市场规则

### 4.1 评分标准：以 Meta 官方报道为例

随着生成式 AI 工具的普及，国际顶尖科技公司逐步调整了面试流程。以 Meta 在公开渠道（Meta Careers / Engineering Blog 关于 Coding Interviews With AI Tools 的报道，官方公开参考日期：2024-10-15，本章节读取复核日期：2026-10-27）披露的 AI 辅助编码轮次为例，考官并不关注“候选人手写语法的速度”，而是考核四大核心维度：

| 考核维度 | 考官核心观察点 | 扣分项 |
|---|---|---|
| **1. 解题与思路（Problem Solving）** | 能够清晰拆解系统与算法逻辑，向 Agent 提供结构化、无歧义的 Prompt 指令 | 盲目把题目全文扔给 AI，自己完全理不清逻辑 |
| **2. 代码质量（Code Quality）** | 能否审查 Agent 生成代码的可读性、分层合理性、命名契约与异常处理规范 | 照单全收劣质实现，代码冗余凌乱 |
| **3. 验证与复核（Verification）** | 具备批判性思维，主动设计反例、边界数据与对抗用例检查 AI 输出 | 看到测试能跑通就直接交卷，遗漏关键边界隐患 |
| **4. 沟通与协作（Communication）** | 能与考官口头讨论权衡取舍（Trade-offs），把 AI 当成结对编程助手而非替罪羊 | 全程沉默无交流，无法解释 AI 编写的代码细节 |

> [!IMPORTANT]
> **注意行业差异**：各公司对于面试中使用 AI 的态度截然不同。有的外企或前沿团队（如 Meta、Shopify 部分岗位）鼓励或专门设置 AI Pair Programming 轮次；而国内绝大多数大厂和很多严谨安全型企业**明确禁止在技术笔试与白板编程中使用任何 AI 工具**，违规将被视为作弊。在进入面试前，务必与招聘 HR 确认该轮次的工具使用规则。

## 5. 绝对禁止交给 Agent 的场景

永远不要因为 Agent 的高效而丧失风险防范底线。以下内容**严禁交给 Agent 或输入到公网大模型上下文**：
- **生产环境密钥与凭据**：API Keys、数据库密码、私钥、OAuth Token。
- **真实生产环境数据与用户 PII**：身份证号、手机号、企业未脱敏财务数据。
- **不可逆的高危操作**：生产环境数据库 `DROP/MIGRATE`、无二次确认的批量删除、集群销毁命令。

## 6. 动手练习：在工单模块中实践 Agent 开发与人工审查

在本练习中，你将使用你熟悉的编码 Agent（Cursor / Claude Code 等）为一个轻量 Python 模块添加分页与筛选功能，并独立完成 diff 审查。

### 6.1 练习目录结构

本章节附带了一个微型代码包 `practice_repo/`：
- `models.py`：工单数据模型与状态枚举。
- `storage.py`：初始工单假数据。
- `service.py`：工单业务逻辑（未完成状态）。
- `TASK.md`：需求说明书（要求支持分页、按状态筛选以及严格的参数校验）。
- `check_task.py`：断言式检查脚本。未打补丁时退出码为 1，满足需求后退出码为 0。

### 6.2 练习步骤

1. **创建独立副本**：
   在工作区创建 `.tmp/practice/` 并将 `practice_repo/` 整体复制过去：
   ```powershell
   Copy-Item -Recurse chapters/part0-setup/0.3-coding-agent-workflow/practice_repo .tmp/practice
   ```
   **不要修改仓库原件**。
2. **引导 Agent 制定计划**：
   在 `.tmp/practice/` 下，让编码 Agent 读取 `TASK.md`，要求其先给出设计思路与修改计划，不要直接动手改代码。将计划要点记录到 [workbook.md](workbook.md)。
3. **执行修改与验证**：
   指示 Agent 修改 `service.py`，并运行：
   ```powershell
   python check_task.py
   ```
   排查错误直到脚本全绿通过（退出码 0）。
4. **独立人工审查 diff**：
   使用 `git diff` 或对比工具审查 Agent 的修改，从范围、边界、防御性、异常处理等角度，找出至少 3 个需要人工复核的点，并找出至少 1 个 Agent 自己遗漏的潜在缺陷。
5. **记录证据**：
   填写 [workbook.md](workbook.md) 中的记录，并按 [gate/CHECKLIST.md](gate/CHECKLIST.md) 自检。
