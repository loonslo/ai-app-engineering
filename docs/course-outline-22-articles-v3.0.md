# 一、先定义课程目标、读者边界和真实毕业标准

## 1.1 目标是“独立交付 AI 应用”，不是“认识 22 个概念”

学习完成后，读者应能把陌生的业务需求转化为可测试的系统：澄清需求 → 选择确定性逻辑或模型 → 开发 API / 数据库 / 前端 → 集成 RAG / Agent / MCP → 设置授权与安全边界 → 评测 → 部署监控 → 故障恢复与维护。

毕业以**可观察的行为**而不是学习天数、框架名称、代码行数或课程完成截图作为依据：

1. 能在没有教程分步提示时实现一个含数据库、权限、异步任务、AI 能力和测试的可运行产品。
2. 能解释模型输出、业务事实、权限校验与外部副作用分别由哪个组件负责，不让 LLM 决定应由代码确定的业务规则。
3. 能用失败案例、代码提交、复现脚本、测试报告与回归数据说明某项改动真正解决了什么。
4. 能完成有限时间内的陌生需求开发、线上故障定位和技术答辩；不以某个阈值直接保证获得 Offer。

岗位定位：**Python AI 应用工程师 / AI 后端工程师 / AI Agent 工程师 / 具备基本前端交付能力的 AI 全栈工程师**。不承诺覆盖模型预训练研究、GPU Kernel、分布式训练或所有前端专家技能。

## 1.2 真零基础与已有开发基础采用同一课程、不同进入方式

**基础预备包（不计入 22 篇正式文章）**：为完全不会编程的读者提供 4 份短手册与可执行练习。

| 预备任务 | 最低独立完成标准 | 不在此阶段深挖 |
|---|---|---|
| P-A Python 基础 | 函数、字典/列表、类、异常、文件、类型注解，写出 50 行数据清洗脚本 | 元类、描述符与复杂设计模式 |
| P-B Web 基础 | 用 HTTP 客户端发 GET/POST，理解状态码、JSON、超时、Cookie、Token 的区别 | TCP 协议栈细节 |
| P-C 开发工具 | 环境管理、依赖锁定、Git 提交/分支、命令行、IDE 调试，能独立复现一个失败测试 | 复杂 GitOps |
| P-D SQL 基础 | 使用 SQL 实现 CRUD、JOIN、事务、简单约束；理解唯一键与索引 | 高级执行计划调优 |

**准入诊断**：能独立调用一个 HTTP API，将 JSON 校验后写入数据库，写出至少 3 个正常/异常测试，再进入阶段 0。不会做的先用预备包补齐。已有 Python 开发经验者可直接参加诊断并跳过预备包。

进度规划只用于安排工作量，不能承诺就业期限：每周 15—20 小时学习者可能需要约 5—10 个月完成正式课程；完全零基础另加基础训练时间。根据每阶段实际验收成绩调整，不按日期强制推进。

## 1.3 唯一主项目：FinOps 企业内部智能报销与工单协同平台

**业务场景**：员工查询报销制度、上传模拟 OCR 票据、提交申请；系统完成规则初审与知识库引用；审批人审核后由**模拟银行/ERP 网关**执行写操作；审计员追溯历史；IT 部门协助工单。所有金额、银行卡、员工信息均为合成测试数据，课程**绝不接真实银行支付接口，也不要求上传真实财务凭证**。

项目随课程自然生长：

```
阶段0：Python / FastAPI / PostgreSQL / pytest 最小业务服务
   ↓
阶段1：原生 LLM + 简单浏览器页 + 强类型解析 + 确定性 Workflow
   ↓
阶段2：制度检索 + 版本更新 + 引用 + 检索权限 + 安全缓存
   ↓
阶段3：原生工具循环 + 有状态 Agent + 人审与副作用对账
   ↓
阶段4：MCP 工具服务 + 多 Agent 选型与收益实验
   ↓
阶段5：认证闭环 + React 工作台 + 长任务与断线续传
   ↓
阶段6：错误归因 + Evals/CI + 可观测性与成本治理
   ↓
阶段7：混沌排障 + 限时新需求 + 陌生领域独立项目
```

重点原则：前期设计的权限占位接口，从阶段 0 起就不能被理解为“真实用户凭据由客户端自己传入”。阶段 0 使用由测试夹具注入的服务端身份，阶段 2 展示授权策略，阶段 4 展示服务间 Token，阶段 5 再完整实现 OIDC/OAuth2 登录体验。

# 二、撰稿与发布必须遵守的 12 条规则

## 2.1 “一节即一篇完整文章”的出版契约

1. **一篇只讲一个中心问题**：一个主要故障、一个可解释的根因、一组必要改动、一套可信验收；附加主题移入“延伸阅读”，不得在正文突然扩展为框架百科。
2. **独立可读**：开篇 100—200 字交代业务背景、简明解释本篇所需的 2—4 个概念；不能只写“上一节已经讲过”。可以标注前置能力，并提供“最小复现快照”使新读者直接跟练。
3. **课程连续**：文末仅简述下一篇需要继承的接口/数据结构；下篇开头重新给出最低背景。独立阅读与体系学习同时成立。
4. **真实问题先于技术名词**：先展示可复现的失败和损失，再说明为什么要使用某项技术；不是先赞美框架后硬编场景。
5. **最小实现必须出现**：读者应先理解不引入复杂框架时，最简单的可运行方案做到了什么、没有做到什么。
6. **分清事实与演示**：必须标注“官方协议行为”“工程建议”“在本机实验的结果”“模拟事故”四种证据级别。模拟数据不能冒充真实生产事故。
7. **结论不得偷换**：JSON Schema 约束结构≠业务事实正确；检索有引用≠引用真正支持论断；测试全部通过≠安全已被证明；HTTPS 公网可访问≠生产就绪。
8. **不杜撰数字和大厂背书**：禁用未经证实的“70% 场景”“提升三倍”“毫秒级必达”“99% 防护”“某公司全部如此实践”等。固定数值只能作为附环境说明的实验条件，或明确的业务约束。
9. **严禁虚假安慰与鸡汤结尾**：禁止“相信自己就能成功”“学会这一招就拿 Offer”“你已经超越 90% 工程师”等；文末写“证据、边界、下一步”，不写空泛情绪价值。
10. **语言遵循第一性原则**：讲事实、讲因果、讲取舍；有必要才引入术语；不东拉西扯、不堆品牌、不重复夸赞技术。区分必要、可选和过度设计。
11. **代码复制后可执行**：标记为 `可运行示例` 的代码片段必须由自动化提取与测试验证；伪代码标为 `设计伪代码`，不能混用。提供完整依赖、Mock 数据、运行命令和预期输出。
12. **面向多平台可重组**：主篇为权威版本；短帖和图文只缩短表达，不扭曲条件和实验结论；附 Git Commit / 测试说明 / 官方引用，禁止为吸引流量制造虚假危机。

## 2.2 强制八段式文章内在结构（以自然随笔展开，不直接生搬大纲编号作为小标题）

每篇文章内在逻辑严格遵循八个环节：
1. **真实需求与背景**：业务目标、输入形式、为什么要做。
2. **最小实现（Happy Path）**：不加复杂度的最简可运行方案。
3. **故障复现**：可控故障注入、失败断言与实际输出。
4. **根因拆解**：依据事件循环、网络、Trace 或数据流定位首个错误边界。
5. **工程修复**：精准修改核心代码，讲清权衡取舍。
6. **自动验收**：A 类业务确定性门禁与 C 类性能/延迟门禁。
7. **局限与替代方案**：说明在何种假设下成立、何时不值得引入、如何退化。
8. **客观结论**：三句以内总结问题、机制与验证结果，不加空泛抒情。

## 2.3 故障靶场与 Git 版本规则

- 每篇独立编号，如 `step-2.2`，建立 `step-2.2-starter`（可运行前置快照）、`step-2.2-broken`（定向故障）、`step-2.2-solution`（经测试的参考实现）。
- 必须提供**固定 Commit SHA**；代码提交采用小幅变更。
- 故障是**有条件必现**：指定数据集、种子、时间控制、并发栅栏和 Mock 行为，保证测试在受控环境复现。
- `broken` 中的危险代码只能运行在隔离容器和虚构账号下；含凭据、转账、越权的实验不可连接生产资产或真实用户数据。
- 最低仓库文件：`README.md`、`pyproject.toml`/锁文件、`.env.example`（无密钥）、`compose.yaml`、`app/`、`tests/`、`fixtures/`、`docs/lesson-XX.md`、`reports/`。
- 优先保留本机无需付费模型的 Mock 路径；真实模型调用作为可选实验。

## 2.4 分层掌握等级

- **L1 独立实现**：不看完整答案可独立写核心算法、工具循环、权限判断、幂等状态转移、数据库事务与测试。
- **L2 理解并集成**：能阅读官方 API、改造给定模板、解释关键调用链、处理典型故障。
- **L3 认知与选型**：能用问题规模、故障模型、成本和团队能力解释何时需要或不需要 Multi-Agent、语义缓存、复杂编排。

## 2.5 A/B/C 三类验收门禁

- **A. 确定性与安全正确性（阻断发布）**：金额计算一致、授权前置、角色撤销阻断、幂等请求键唯一、未批准不得执行、异常事务回滚、凭据不入日志。给定输入必须全部通过。
- **B. 模型/检索统计质量（基于数据校准）**：Hit@K、Recall@K、误拒/漏拒、Task Success Rate、Judge 的 FPR/FNR、攻击成功率。公开样本数、分布、基线、置信范围与失败样例。
- **C. 性能成本（环境条件下验收）**：TTFT、p50/p95、吞吐量、Token 成本、缓存命中率、数据库执行计划。明确测试硬件环境与实验条件。

## 2.6 技术事实核对与安全基本规范

- 每篇最少一个**一级来源**：官方规范、源码、标准、权威工程文档。
- 原始 PDF / 文本可能包含间接 Prompt 注入；模型读取内容不等于授予其工具执行权限。
- LLM 不能自行签发审批、修改权限、转账。高风险动作由服务端验证身份、资源范围、审批记录、提案版本和可重复执行性。
- 金额用 `Decimal` 或数据库 `NUMERIC`，金额加总与汇率折算由确定性代码完成。LLM 只负责信息抽取和解释。
- OAuth2/OIDC、JWT、RBAC 是不同概念；服务端 `SecurityContext` 只能来自已认证身份或固定测试夹具。

# 四、八个阶段的详细设计与产出契约

## 阶段 0：工程准入（3 篇）
- **0.1** 为什么 `async def` 里的阻塞调用会拖慢全部请求？——从脏发票校验到异步限流
  - 核心：Pydantic V2 校验、`httpx.AsyncClient` 复用、`asyncio.Semaphore` 限流、逐请求超时与错误分类。
  - 产出：`invoice_models.py`、`invoice_batch.py`、`course/lesson_01/test_0_1.py`。
- **0.2** 并发报销为什么会把预算扣成负数？——FastAPI 事务与数据库锁
  - 核心：FastAPI 路由与依赖注入、SQLAlchemy 2.x `AsyncSession`、行锁/乐观锁、事务整体回滚。
  - 产出：`expense_api.py`、Alembic 迁移、并发回归测试。
- **0.3** 没有真实外部接口，怎么证明代码可靠？——pytest、Mock、Git 与 Docker
  - 核心：pytest fixture、`respx`、测试数据库隔离、Docker Compose 依赖本地启动。
  - 产出：`compose.yaml`、`tests/`、Makefile 与自动化测试流水线。

## 阶段 1：LLM 基础与确定性工作流（3 篇）
- **1.1** 浏览器点击“停止”，为什么模型还在继续生成？——原生 LLM API 与 SSE
  - 核心：原生 SDK 异步调用、FastAPI SSE 流式传输、客户端 AbortController 取消与服务端取消监听。
  - 产出：SSE 接口、`debug-ui.html`、取消测试。
- **1.2** 模型输出是合法 JSON，为什么还是报销错账？——Schema 与业务语义校验
  - 核心：Structured Outputs、Pydantic 业务语义校验、Decimal 计算、有界反馈重试。
  - 产出：`ExpenseClaim`、`claim_validator.py`、差错样本集。
- **1.3** 什么时候根本不需要 Agent？——串行、路由与并行 Workflow 的成本实验
  - 核心：Chaining、Routing、Parallelization，代码规则与大模型调用的边界与成本对比。
  - 产出：`review_workflow.py`、耗时与成本对比报告。

## 阶段 2：RAG 检索、知识生命周期与权限（2 篇）
- **2.1** 为什么搜索报销条款号却找不到制度？——从最小 RAG 到混合检索与版本更新
  - 核心：Markdown/PDF 表格分块、向量检索 + PostgreSQL FTS 混合召回、RRF 排序、文档版本管理与软删除清理。
  - 产出：`ingest.py`、`retriever.py`、`citations.py`。
- **2.2** 为什么高管的 RAG 答案会泄露给实习生？——预授权检索、撤权与安全缓存
  - 核心：服务端 VerifiedPrincipal 身份上下文、预授权向量过滤、缓存键版本化隔离、撤权失效、敏感问答不共享。
  - 产出：`security_context.py`、`authorized_retriever.py`、`cache_policy.py`、越权红队测试。

## 阶段 3：从原生工具循环到可靠 Agent（3 篇）
- **3.1** Agent 究竟怎么调用工具？——自己写一个带防错机制的原生 Tool Loop
  - 核心：原生 Tool Loop、参数校验、结构化错误回填、最大步数与循环检测、只读工具白名单。
  - 产出：`tool_loop.py`、模拟业务工具集、轨迹测试。
- **3.2** 服务器重启后，Agent 为什么丢失工作进度？——LangGraph 状态图与恢复边界
  - 核心：State、Nodes、Conditional Edges、Postgres Checkpointer、重启恢复与 thread_id。

- **3.3** 审批通过后为何还会重复打款？——`interrupt()`、提案冻结与幂等对账
