- **目标**：先定义问题与成功标准，再写代码：访谈潜在用户，写 1 页 PRD，定义指标与 golden set 的来源。
- **v3 路径**：P1 / 项目（清单验收）
- **岗位任务 / 面试题型**：T6 / F3、F6
- **节奏**：4 小时，第 5 周完成。
- **前置**：无硬性前置；有 [L0.5 岗位地图](../../part0-setup/0.5-job-map-gap/README.md)的目标岗位更好。

## 为什么

很多 AI 项目在写第一行代码之前就已经失败了：没有明确的用户和工作流，没有成功标准，也没有办法知道它有没有变好。两份公开调查可以作为背景，但要注意它们的性质：

- **MIT NANDA《The GenAI Divide: State of AI in Business 2025》**（2025-07，读取于 2026-10-31）：作者自述为“初步发现”，方法是回顾 300 多个公开的 AI 项目、访谈 52 家组织、并在四场行业会议上收集 153 位高管的问卷。它认为企业级系统多数失败于“脆弱的工作流、缺少上下文学习、与日常运作不匹配”，而不是模型质量或监管。样本和方法有明显局限，只能当作一种观点，不是定论。
- **Anthropic 与 Material《The 2026 State of AI Agents Report》**（调查于 2025 年末，读取于 2026-10-31）：调查了 500 多位美国技术负责人；报告把规模化的主要挑战列为集成（46%）、数据质量（42%）、变更管理（39%）。这是**厂商调查**，发布方是模型厂商，问题设计与解读都带立场。

两份材料指向同一个方向：问题在于**和真实工作流的结合**。至于“上线成本没有预估”，是本课程的工程经验判断，上面两份材料没有这样的结论，不要当作它们的发现来引用。

## 步骤

1. **找问题和用户**：选一个你能接触到真实用户的场景（同事、测试团队、社区）。先找人，再定方案。
2. **访谈至少 2 位潜在用户**，用 [访谈提纲](templates/stakeholder-interview.md)。问“最近一次”，不要问“你会不会用”：
   - 最近一次遇到这个问题是什么时候？当时怎么解决的？花了多久？
   - 现在最麻烦的一步是什么？出错了怎么办、谁来兜底？
   - 一个“够好”的答案长什么样？什么情况下你宁可不要答案？
3. **写 1 页 PRD**（[模板](templates/prd-1page.md)）：问题、用户、范围与非目标、成功指标、约束、风险。
4. **定义指标**（[模板](templates/metrics-definition.md)）。指标分四类：
   - 质量：引用正确率、拒答正确率、字段准确率；
   - 延迟：p95；
   - 成本：单次请求成本；
   - 采用：真实用户数、请求数。
   每个指标要写清计算方式、数据来源、门槛和采集频率。**没有采集方式的指标不算指标。**
5. **定义 golden set 的来源**：来自真实问题和真实失败，而不是你自己想出来的题。先收集 20–30 条，后续逐步扩到 ≥50 条（E1 要求）。
6. 把 E1 的目标数（≥5 个真实用户、≥200 次真实请求、p95、单次请求成本、缓存命中率、golden set ≥50、judge 标注 ≥30）写进指标定义，作为你自己的目标。

## 产物与验收

见 [CHECKLIST](gate/CHECKLIST.md)。验收看四点：访谈记录是真实的（有日期和代号，不是编的）；PRD 里有明确的非目标；每个指标都有采集方式；golden set 的来源是真实问题。

## 常见失败

- 没有用户就开始写代码，做完发现没人要；
- 指标写了“准确率高”，没有定义怎么算、拿什么数据算；
- 只问“你觉得这个想法怎么样”，得到的都是客气的肯定；
- 用自己的测试请求充当“真实用户数据”。

## 边界

- 本章是规划与记录，没有可执行检查；它不能替你找到用户，也不能证明需求真实存在。
- 上面两份调查的数字只用来说明背景，不能当作你的项目的成功概率或收益依据。
